### Recovery defects fixed during execution

The following defects were identified during planning and are now fixed with regressions and real MCP transport checks. Their original failure modes and required invariants remain below for review.

1. **P1 — Preserve corrupt or quarantined v2 data.** `loadSessions` retains malformed top-level records only in the in-memory restore report; a later save or capacity normalization can overwrite the original without retaining them. Parse/version failures only log and do not populate user-visible recovery status. Back up original bytes or persist a quarantine sidecar before any rewrite; expose safe restore status and recovery export. Test mixed valid/invalid v2 records, corrupt JSON, unsupported versions, capacity normalization and subsequent saves. Backup/write failure must leave original data recoverable.
2. **P1 — Do not certify lost physical state through configuration reconciliation.** `markDamaged` keeps legacy integrity as `legacy-unverified`, but applying a configuration-only reconciliation sets the whole workspace to `verified` and clears warnings. Separate provenance uncertainty from lost configuration/layout/reference data. Keep hard-loss designs gated, or verify and record trust per scope. A successful configuration derive must not unlock full-workspace export/validation when rack, cable, floor or PDU references were quarantined.
3. **P2 — Correct remote-success diagnostics for reconciliation proposals.** `proposeReconciliation` records proposal metadata after a remote derive without passing persistence context. Supply `remoteApplied:true` and actionable recovery context; assert one remote request, no proposal publication and no raw disk-error leakage on write failure.

Source locations: [session loading](../../src/session/persist.ts), [restore and quarantine](../../src/session/SessionStore.ts), [reconciliation trust](../../src/domain/reconciliation.ts), and [proposal persistence](../../src/mcp/service.ts). Configuration reconciliation preserves physical-state trust boundaries and blocks hard-loss recovery records. ## Implementation decisions

1. **One canonical state.** Retain the full DCSC response and a separate client-owned overlay for quantity, controls, role and preferences. Retain the full workspace envelope for layout, floor, network and standalone data. Build indexes and concise tool views from it. Never mutate a read projection or use it as the authoritative request model.
2. **Explicit serializers.** Separate auto-derive, validation and export envelopes around shared configuration/group serialization. Preserve section/result types, software anchors, service metadata, associated products and upstream fields required for round trips. Do not blindly submit every raw response field.
3. **Atomic workspace transactions.** Resolve scope, acquire the workspace lock, check `expectedRevision`, clone a draft, perform the operation, verify acceptance, then commit once. Failures discard the draft. Snapshot pristine state. Internal helpers must avoid reacquiring the same lock. Reads see a committed revision.
4. **Durable success.** Under the transaction lock, persist the validated candidate snapshot before publishing its in-memory state and returning success. Serialize whole-store writes so transactions in different workspaces cannot overwrite each other's changes. An I/O failure discards the local candidate. Use atomic file replacement and flush on shutdown. If a remote side effect already happened, return explicit `remoteApplied/localNotCommitted` recovery diagnostics instead of silently retrying the whole mutation. Persistence-disabled mode commits locally with that durability limitation visible.
5. **Clear quantities and identities.** Sales quantity, physical instances and associated-product/licensing quantities are distinct. One authoritative configuration ID is rewritten into known wire identity fields and maps. Normalize product identity using the first nonempty valid code. Enforce workspace membership, locale and solution mode.
6. **Honest validation and calculations.** Return explicit validation status and provenance. `isValid` is true only for a confirmed successful terminal result at the current revision. Reject mixed-currency comparison; return currency everywhere. No implicit foreign-exchange service or guessed infrastructure totals.
7. **Compatible tool evolution.** Keep existing tool names and useful single-configuration shortcuts. Add fields and discrete missing operations. Require an explicit target when a workspace has several possible targets; never silently pick its first configuration. Update descriptions, examples and actionable `next` arguments together.
8. **Safe saved-state migration.** Back up v1 files, validate the complete migration before replacement, preserve handles, rebuild projections and surface integrity warnings. Do not silently relaunch designs or claim to reconstruct service selections already lost by the old serializer. Reconciliation produces a reviewable diff before applying changes.
